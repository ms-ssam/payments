# 결제 승인·취소 정합성 개선(트러블슈팅) 계획 — 요약

## 배경
현재 `PaymentService`의 승인(`confirmPayment`)과 취소(`cancelPayment`)는 **"DB 조회 → 토스 호출 → DB 쓰기"를 하나의 `@Transactional`에 묶은 구조**다. 토스 호출은 DB 롤백으로 되돌릴 수 없는 외부 작업이라, 토스 처리 후 DB 쓰기·커밋이 실패하면 **토스와 우리 DB의 상태가 어긋나고, 이를 다시 맞출 장치도 없다.** 또 토스 응답을 기다리는 동안 DB 락·커넥션을 계속 점유한다.

## 문제 목록

| # | 문제 | 결과 | 심각도 |
|---|---|---|---|
| 1-1 | 승인 시 재고 차감(UPDATE)으로 잡은 상품 row 락을 쥔 채 토스 호출 | 같은 상품 결제·취소가 토스 응답까지 줄줄이 대기 | 높음 |
| 1-2 | 토스 클라이언트에 connect/read 타임아웃 없음 | 토스 지연 시 락·커넥션 장시간 점유 | 높음 |
| 1-3 | 실패 기록(`markFailed`, `REQUIRES_NEW`)이 커넥션을 하나 더 사용 | 커넥션 풀 고갈 위험 | 중간 |
| 2-1 | 토스 승인 성공 후 DB 쓰기·커밋 실패 | 고객 돈은 빠졌는데 주문 `PENDING`, Payment·원장 없음 | 높음 |
| 2-2 | 토스 승인 요청 타임아웃·네트워크 오류(`TossApiException` 아님) | 실제 승인 여부를 모른 채 롤백 → 2-1과 같은 상태 가능 | 높음 |
| 2-3 | 2-1·2-2 후 재시도 시 `ALREADY_PROCESSED_PAYMENT` 분기에서 `increaseStock()` | **`PAID`인데 재고가 한 번도 차감되지 않음** (현재 코드 버그) | 높음 |
| 2-4 | 토스 에러를 모두 확정 실패로 처리 (5xx, JSON 아닌 에러 본문 포함) | 승인 여부가 불확실한데 `FAILED`로 굳음 | 중간 |
| 2-5 | 토스 환불 성공 후 DB 쓰기·커밋 실패 | 환불됐는데 `PAID`, 재고·원장·환수 미반영 | 높음 |
| 2-6 | 2-5 후 다시 취소하면 토스가 이미 취소된 결제라며 에러 | 시스템 안에서 영영 복구 불가 | 높음 |
| 2-7 | 취소가 토스 응답을 기다리는 사이 구매확정이 먼저 커밋 | 환불됐는데 `CONFIRMED` + 매출 인식 | 중간 |
| 2-8 | 취소와 정산 배치 경합 (`Payment`에 락·버전 없음) | 원장 미수금 이중 차감, 환수 기록 누락 | 중간 |

**원인 정리**
- **원인 A — 토스 호출과 DB 반영을 한 트랜잭션에 묶음**: 1-1, 1-3, 2-1, 2-2, 2-4, 2-5, 2-7
- **원인 B — 토스 실제 상태를 다시 확인하는 장치 없음**: 2-1, 2-2, 2-6
- **개별 문제**: 1-2(타임아웃), 2-8(정산 경합)
- 2-3은 원인 A를 땜질한 분기에서 생긴 버그라, 원인 A를 해결하면 같이 사라진다.

## 유지하는 결정
- **재고 차감 → 토스 승인 순서는 유지한다.** 반대로 하면 재고가 없을 때 이미 빠져나간 돈을 환불해야 하고, 마지막 재고 경합 시 여러 명에게 승인 후 환불이 발생한다. 문제는 순서가 아니라 **같은 트랜잭션 안에서 락을 쥔 채 토스를 기다린다는 점**이다.

## 개선 방향
핵심은 **트랜잭션 경계를 나누는 것**이다. 승인·취소를 **"트랜잭션1 커밋 → 토스 호출(트랜잭션 밖) → 트랜잭션2 커밋"** 세 단계로 나누면, 토스 응답을 기다리는 동안 락·커넥션을 잡지 않고, 중간에 문제가 생겨도 주문이 "진행 중" 상태로 남아 어디서 멈췄는지 알 수 있다.

현재 `confirmPayment`의 `ALREADY_PROCESSED_PAYMENT` 분기(2-3 버그 포함)는 이 구조 문제를 땜질한 코드다. 구조를 바꾸면 이 분기는 새로 짜게 되므로, **2-3·2-6은 따로 패치하지 않고 구조 개선에 흡수한다.**

단, 트랜잭션 경계를 나눠도 **토스 결과를 알 수 없는 경우(read timeout 등)는 여전히 생긴다.** 이건 진행 중 상태로 남겨두고 대사 배치(나중엔 웹훅도)가 토스에 조회해 정리한다.

**타임아웃 ≠ 결과 불명 해결책**: 타임아웃은 기다리는 시간에 상한을 둬서 스레드·커넥션을 지키는 장치로, 외부 호출엔 항상 필요하다. 하지만 타임아웃으로 포기해도 토스 결과를 알게 되는 건 아니고, 오히려 "무한 대기"를 "N초 뒤 결과 불명"으로 바꿀 뿐이다. 결과 불명을 실제로 해결하는 건 토스의 실제 결과를 알아내는 장치(대사 배치, 웹훅)다.

## 작업 순서

### 1. 토스 클라이언트 타임아웃 (1-2)
- `RestClient` 생성 시 connect/read 타임아웃 지정. 값은 토스 권장값 확인 후 결정.
- 몇 줄짜리 독립 작업이고, 2번의 결과 분류가 connect/read timeout을 구분해 처리하므로 먼저 한다.

### 2. 승인 트랜잭션 분리 (1-1, 1-3, 2-1, 2-2, 2-3, 2-4)
모든 결제가 거치는 경로라 효과가 가장 크다.
```
[트랜잭션1] 상태·금액 검증 + 재고 차감 + 주문 PENDING → APPROVAL_REQUESTED, paymentKey 저장 → 커밋(락 해제)
[트랜잭션 밖] 토스 confirm 호출
[트랜잭션2] 성공      → PAID + Payment 저장 + 원장 분개
            확정 실패 → FAILED + 재고 복구(명시적)
            결과 불명 → APPROVAL_REQUESTED 유지 (4번 배치가 정리)
```
- **결과 분류**: 결과 불명을 실패로 단정하지 않는다(2-4 해결).

  | 분류 | 해당 경우 | 이유 |
  |---|---|---|
  | 성공 | 토스 승인 응답 | |
  | 확정 실패 | 토스 4xx 업무 에러(카드 거절 등), **connection timeout** | connection timeout은 연결 자체가 안 돼 요청이 토스에 도달하지 않았으므로 결과가 확실함 |
  | 결과 불명 | **read timeout**, 응답 중 연결 끊김, 5xx, 에러 본문 파싱 실패, `ALREADY_PROCESSED_PAYMENT` | 요청은 토스에 도달했을 수 있어 실제 처리 여부를 모름 |
- **상태 추가**: `OrderStatus`에 `APPROVAL_REQUESTED`. 토스 승인을 뜻하는 이름에 "CONFIRM"을 쓰지 않는다 — 구매확정(`CONFIRMED`)과 헷갈리기 때문.
- **`paymentKey`를 트랜잭션1에서 저장**: 결과 불명 상태에서도 토스 결제 조회가 가능해야 하므로 Order에 저장(또는 요청 상태의 Payment를 먼저 생성).
- **중복 콜백**: `APPROVAL_REQUESTED` 상태에 success 콜백이 다시 오면 토스를 다시 호출하지 않고 현재 상태를 반환. 트랜잭션1이 토스 호출 전에 커밋되므로 "토스는 승인됐는데 주문은 `PENDING`"인 상태가 생기지 않고, 기존 `ALREADY_PROCESSED_PAYMENT` 분기와 `increaseStock()`이 필요 없어진다(2-3 해결).
- **트레이드오프**: 실패 시 롤백으로 재고가 저절로 복구되던 장점이 사라져, **재고 복구 코드를 직접 작성**해야 한다. 실패 기록도 트랜잭션2에서 하므로 `REQUIRES_NEW`가 필요 없어진다(1-3 해결).

### 3. 취소 트랜잭션 분리 (2-5, 2-6, 2-7)
2번과 같은 패턴.
```
[트랜잭션1] PAID 확인 → CANCEL_REQUESTED → 커밋
[트랜잭션 밖] 토스 cancel 호출
[트랜잭션2] 성공      → CANCELED + 재고 복구 + 원장/환수
            확정 실패 → PAID로 되돌림
            결과 불명 → CANCEL_REQUESTED 유지 (4번 배치가 정리)
```
- **상태 추가**: `OrderStatus`에 `CANCEL_REQUESTED`.
- 환불 후 트랜잭션2가 실패해도 주문은 `CANCEL_REQUESTED`로 남는다. 재취소 요청은 `PAID`가 아니라서 토스까지 가지 않으므로 "이미 취소된 결제" 에러로 막히는 일이 없다(2-6 해결). 남은 정리는 4번 배치가 한다.
- `CANCEL_REQUESTED` 동안은 상태가 `PAID`가 아니므로 구매확정이 막힌다(2-7 해결).

### 4. `reconcile()` + 대사 배치 (원인 B 해결)
2·3번에서 진행 중 상태로 남은 주문을 정리하는 마무리 작업. 2·3번이 끝나야 정리할 대상이 생긴다.
- **`reconcile(order)`**: 토스 결제 조회로 실제 상태를 확인해 DB를 맞추는 단일 메서드. 이미 같은 상태면 아무것도 하지 않는다(멱등).
  - `APPROVAL_REQUESTED` + 토스 `DONE` → 승인 성공 처리 / 토스 미승인 → 실패 처리 + 재고 복구
  - `CANCEL_REQUESTED` + 토스 `CANCELED` → 취소 완료 처리 / 토스 `DONE` → `PAID`로 되돌림
- **대사 배치**: `@Scheduled`(예: 5분)로 진행 중 상태에 일정 시간 이상 머문 주문만 조회해 `reconcile()` 호출.
  - 평소엔 조회 결과가 0건이라 DB 쿼리 1회로 끝나고 토스와 통신하지 않는다. 장애가 난 건만 토스에 조회한다.
  - 상태 변경 시각 컬럼 필요(현재 Order엔 없음 → `updatedAt` 등 추가) + `(status, 변경시각)` 인덱스.

### 5. 나중에
- **2-8**: 정산 배치와 취소가 같은 Payment를 동시에 다루지 않도록 Payment에 `@Version` 또는 조회 락 적용. 토스 호출과 무관한 별개 문제.
- **웹훅**: 토스 상태 변경 이벤트 수신 → `reconcile()` 재사용. 웹훅 내용은 신뢰하지 않고 결제 조회로 재확인.
  - 실무에선 결과 불명 정리를 웹훅(빠름, 주력) + 대사 배치(놓친 것 정리, 안전망)로 함께 한다. 웹훅만으로는 우리 서버 다운·전달 실패 시 놓칠 수 있다.
  - 이 프로젝트에선 웹훅이 외부에서 접속 가능한 URL을 요구해(`localhost`는 ngrok 등 터널링 필요) 대사 배치를 먼저 만들고 웹훅은 나중에 붙인다. 같은 `reconcile()`을 쓰므로 순서를 바꿔도 다시 짤 부분은 없다.
  - 어떤 결제수단·상태 변화에 웹훅이 오는지는 토스 문서에서 확인 필요.
- **`Idempotency-Key`**: 토스 승인·취소 재시도 시 중복 처리 방지.

## 검증
- 1: 토스 응답 지연을 흉내 냈을 때 설정한 시간 안에 예외로 끝나는지 확인.
- 2: 토스 응답 지연 중 같은 상품의 다른 결제가 대기 없이 진행되는지 확인. `TossPaymentClient` stub으로 성공/확정 실패/결과 불명 각각의 최종 상태·재고·원장 확인. 진행 중 상태에서 success 콜백 재도달 시 토스를 다시 호출하지 않는지 확인.
- 3: stub으로 성공/확정 실패/결과 불명 각각의 최종 상태·재고·원장·환수 확인. `CANCEL_REQUESTED` 중 구매확정·재취소가 거부되는지 확인.
- 4: 진행 중 상태로 남긴 주문이 배치 실행 후 토스 상태와 일치하는지 확인.
